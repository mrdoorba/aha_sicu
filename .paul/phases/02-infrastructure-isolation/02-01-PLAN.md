<objective>
## Goal
Eliminate shared database credentials between dev and prod, and migrate Terraform state from local backend to GCS — fixing the two infrastructure isolation failures identified by AEGIS.

## Purpose
Dev and prod currently share the same DB user (`aha_sicu`) and password. A credential leak in dev immediately compromises prod with no audit trail separation. Terraform state is stored locally with no locking or shared access, making infrastructure knowledge irrecoverable without the original developer. These are the remaining CRITICAL and MEDIUM findings from the AEGIS audit.

## Output
- Per-environment DB users (`aha_sicu_dev`, `aha_sicu_prod`) with independent passwords
- GCS-backed Terraform state with locking
- Removal of shared `random_password.db` and `google_sql_user.app` from root
</objective>

<task type="auto">
  <name>Task 1: Move DB credentials into environment module</name>
  <files>
    infrastructure/terraform/cloud_sql.tf,

    infrastructure/terraform/variables.tf,
    infrastructure/terraform/modules/environment/main.tf,
    infrastructure/terraform/modules/environment/variables.tf
  </files>
  <action>
    **In `modules/environment/main.tf`:**
    1. Add `random_password.db` resource (length=24, special=true) inside the environment module
    2. Add `google_sql_user.app` resource with:
       - name = "aha_sicu_${var.environment}" (per-env username)
       - instance = var.cloud_sql_instance_name
       - password = random_password.db.result
       - project = var.project_id
    3. Update the existing `google_secret_manager_secret_version.db_password` to use `random_password.db.result` (it already does via `var.db_password` — we'll change it to use the local resource directly)
    4. Add `DB_USER` env var to Cloud Run container using the new per-env username:
       - Change `value = var.db_user` to `value = google_sql_user.app.name`
    5. Add `depends_on` for the new `google_sql_user.app` to the Cloud Run service

    **In `modules/environment/variables.tf`:**
    1. Remove `variable "db_user"` (no longer passed from root)
    2. Remove `variable "db_password"` (generated internally now)

    **In `cloud_sql.tf`:**
    1. Remove `random_password.db` resource
    2. Remove `google_sql_user.app` resource — BUT add a `removed` block to prevent Terraform
       from destroying the old shared user during apply. The old user must stay alive until
       per-env users are verified working. Use: <!-- audit-added -->
       ```hcl
       removed {
         from = google_sql_user.app
         lifecycle {
           destroy = false
         }
       }
       ```
       This tells Terraform to stop managing the resource without destroying it.
       The old user can be cleaned up manually after verifying per-env users work.
    3. Keep `google_sql_database_instance.main` and scheduler resources untouched

    **In root `main.tf`:**
    1. Remove `db_user = var.db_user` from both module "dev" and module "prod" calls
    2. Remove `db_password = random_password.db.result` from both module calls

    **In root `variables.tf`:**
    1. Remove `variable "db_user"` (no longer needed at root level)

    **Avoid:**
    - Do NOT touch Cloud SQL instance itself (google_sql_database_instance.main)
    - Do NOT modify the scheduler start/stop jobs
    - Do NOT change any non-DB env vars in Cloud Run
    - Do NOT remove the cloud_sql_instance_name or cloud_sql_instance_connection_name variables
  </action>
  <verify>
    cd infrastructure/terraform && terraform fmt -check -recursive && terraform validate
    (Validation may warn about missing provider config — that's expected without tfvars.
    The key check is syntax validity and no undefined variable references.)
  </verify>
  <done>AC-1, AC-2, AC-3 satisfied: Each environment module creates its own DB user and password independently</done>
</task>

  <name>Task 2: Add GCS state bucket and switch backend</name>
  <files>
    infrastructure/terraform/main.tf,
    infrastructure/terraform/state.tf
  </files>
  <action>
    **In `main.tf`:**
    1. Replace the backend block:
       - Remove `backend "local" {}`
       - Uncomment and use: `backend "gcs" { bucket = "aha-coms-sicu-terraform-state" prefix = "terraform/state" }`

    **Create new file `state.tf`:** <!-- audit-added: separate from cloud_sql.tf -->
    1. Add a `google_storage_bucket` resource for the state bucket:
       - name = "aha-coms-sicu-terraform-state"
       - location = var.region
       - project = var.project_id
       - uniform_bucket_level_access = true
       - public_access_prevention = "enforced"
       - versioning { enabled = true } (for state history/recovery)
       - lifecycle_rule: delete noncurrent versions after 30 days

    **Note:** The GCS bucket must exist BEFORE `terraform init -migrate-state` can work.
    This creates a chicken-and-egg problem. The bucket resource is declared for future management,
    but the actual bucket must be created manually first (or via gcloud) before migration.

    **Avoid:**
    - Do NOT add force_destroy on the state bucket
    - Do NOT add lifecycle rules that delete current versions
  </action>
  <verify>
    terraform fmt -check -recursive

  </verify>

<task type="checkpoint:human-action" gate="blocking">
  <name>Checkpoint: Migrate Terraform State to GCS</name>
  <what>Terraform state must be migrated from local to GCS. This requires manual steps because the GCS bucket must exist before `terraform init` can use it as a backend.</what>
  <how-to-execute>
    **Phase A: State Migration**
    1. Back up current local state: <!-- audit-added -->
       ```bash
       cd infrastructure/terraform
       cp terraform.tfstate terraform.tfstate.pre-migration-backup
       ```
    2. Create the GCS bucket (if it doesn't exist):
       ```bash
       gcloud storage buckets create gs://aha-coms-sicu-terraform-state \
         --project=YOUR_PROJECT_ID \
         --location=asia-southeast2 \
         --uniform-bucket-level-access \
         --public-access-prevention
       ```
    3. Migrate state:
       ```bash
       terraform init -migrate-state
       ```
       Terraform will ask: "Do you want to copy existing state to the new backend?" → Yes
    4. Validate everything still resolves:
       ```bash
       terraform validate && terraform plan
       ```
       Plan should show the new per-env DB users to create + state bucket to import.
       It should NOT show the old shared user being destroyed (thanks to the `removed` block).

    **Phase B: Apply and Verify Per-Env Users** <!-- audit-added -->
    5. Apply the changes:
       ```bash
       terraform apply
       ```
       This creates per-env DB users. The old shared user remains alive (unmanaged).
    6. Verify new users can connect from both environments.
    7. Redeploy Cloud Run in both environments (CI/CD will pick up new DB_USER).

    **Phase C: Cleanup Old Shared User** <!-- audit-added -->
    8. After both environments are verified working with new users, delete old shared user:
       ```bash
       gcloud sql users delete aha_sicu --instance=aha-sicu-db --project=YOUR_PROJECT_ID
       ```
    9. Remove the `removed` block from `cloud_sql.tf` (it's no longer needed).
    10. Delete local state backup:
       ```bash
       rm -f terraform.tfstate terraform.tfstate.backup terraform.tfstate.pre-migration-backup
       ```

    **Rollback Plan (if things go wrong):** <!-- audit-added -->
    - **State migration failed:** Restore from backup:
      ```bash
      cp terraform.tfstate.pre-migration-backup terraform.tfstate
      ```
      Revert `main.tf` backend to `local {}`, run `terraform init`.
    - **New DB users can't connect:** Old shared user is still alive.
      Revert Cloud Run DB_USER to old value via manual env var update or revert + redeploy.
    - **Partial apply:** `terraform plan` will show remaining drift. Re-run `terraform apply`.
  </how-to-execute>
  <resume-signal>Type "done" after completing the migration, or "skip" to defer to a later session</resume-signal>
</task>
