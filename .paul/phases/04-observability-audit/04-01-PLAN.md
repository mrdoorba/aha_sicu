<objective>
## Goal
Add structured JSON logging with request correlation IDs, request/access logging middleware, and PostgreSQL audit flags — establishing the observability foundation for incident investigation and compliance.

## Purpose
The application currently has zero observability: plain-text logs, no request correlation, no access logging, and no database-level audit trail. This makes post-deploy validation, incident investigation, and compliance auditing impossible. This plan addresses 5 of 6 Phase 4 findings.

## Output

- `backend/app/core/middleware.py` — Extended with request logging middleware
- `backend/app/main.py` — Wired structured logging + middleware
- Unit tests for logging and middleware
- Terraform PostgreSQL logging flags
</objective>

<acceptance_criteria>

## AC-1: Structured JSON Logging
```gherkin
Given the application is running
When any log statement is emitted
Then the output is a single-line JSON object with keys: severity, message, logger, timestamp, request_id
```

## AC-2: Request Correlation IDs
```gherkin
Given a request arrives at the API
When the request is processed
Then a unique request_id is generated (or extracted from X-Request-ID header)
And the request_id appears in all log entries for that request
And the response includes an X-Request-ID header with the same value
```

## AC-3: Request Access Logging
```gherkin
Given any HTTP request completes
When the response is sent
Then a structured log entry is emitted with: method, path, status_code, duration_ms, request_id
And the log severity is INFO for 2xx/3xx, WARNING for 4xx, ERROR for 5xx
```

## AC-3a: Middleware Resilience During Exceptions <!-- audit-added -->
```gherkin
Given a request that triggers an unhandled exception in the handler
When the global exception handler returns a 500 response
Then the middleware still emits an access log with status_code=500 and duration_ms
And the X-Request-ID header is still present on the error response
And the correlation ID context is properly cleaned up
```

## AC-4: Health Endpoint Excluded from Access Logs
```gherkin
Given a request to /health
When the response is sent
Then no access log entry is emitted (avoids log noise from readiness probes)
```

## AC-5: PostgreSQL Logging Flags Configured
```gherkin
Given the Cloud SQL Terraform configuration
When terraform plan is run
Then database_flags include: log_connections=on, log_disconnections=on, log_checkpoints=on, log_statement=mod, log_min_duration_statement=1000
```

  <name>Task 1: Create structured JSON logging module</name>
  <files>backend/app/core/logging.py, backend/app/main.py, backend/tests/unit/test_logging.py</files>
  <action>
    Create `backend/app/core/logging.py`:
    - Define `request_id_var: ContextVar[str]` with default "no-request"
    - Implement `JSONFormatter(logging.Formatter)` that outputs single-line JSON with keys:
      - severity (from record.levelname)
      - message (from record.getMessage())
      - logger (from record.name)
      - timestamp (ISO 8601 format)
      - request_id (from request_id_var.get())
      - exception (from formatException, only if exc_info present)
    - Implement `setup_logging(level: str = "INFO")` function that:
      - Accepts log level as parameter (from settings.log_level)
      - Creates a StreamHandler with JSONFormatter
      - Replaces root logger config (removes basicConfig handler)
      - Sets level from parameter (validated against logging constants)

    Add to `backend/app/config.py`: <!-- audit-added -->
    - Add `log_level: str = "INFO"` field to Settings class
    - This allows operations to switch to DEBUG via LOG_LEVEL env var without redeploying

    Modify `backend/app/main.py`:
    - Replace `logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(name)s: %(message)s")` with import and call to `setup_logging(settings.log_level)` <!-- audit-added: pass configurable level -->
    - Import from `app.core.logging`

    Create `backend/tests/unit/test_logging.py`:
    - Test JSONFormatter produces valid JSON with all required keys
    - Test request_id_var value appears in formatted output
    - Test exception info is included when present
    - Test setup_logging respects configurable log level <!-- audit-added -->

    Avoid: Do NOT use third-party logging libraries (python-json-logger, google-cloud-logging) — stdlib is sufficient and avoids new dependencies.
  </action>

<task type="auto">
  <name>Task 2: Add request logging middleware with correlation IDs</name>
  <files>backend/app/core/middleware.py, backend/app/main.py, backend/tests/unit/test_request_middleware.py</files>
  <action>
    Extend `backend/app/core/middleware.py`:
    - Keep existing `app_exception_handler` unchanged
    - Add `RequestLoggingMiddleware(BaseHTTPMiddleware)`:
      - In dispatch():
        1. Extract request_id from X-Request-ID header, or generate uuid4()
        2. Set request_id_var context var (from app.core.logging)
        3. Record start time using `time.monotonic()` (NOT `time.time()` — wall clock drifts with NTP) <!-- audit-added -->
        4. Wrap call_next(request) in try/except to handle unexpected errors <!-- audit-added -->
           - On exception: log at ERROR level, re-raise (global handler will produce 500 response)
           - The finally block ensures correlation ID cleanup regardless of success/failure
        5. Calculate duration_ms from monotonic delta <!-- audit-added: monotonic -->
        6. If path != "/health": emit structured access log with method, path, status_code, duration_ms
        7. Set X-Request-ID response header
        8. Reset context var token in finally block
      - Log severity: INFO for status < 400, WARNING for 4xx, ERROR for 5xx

    Modify `backend/app/main.py`:
    - Import and add RequestLoggingMiddleware BEFORE CORSMiddleware (so it wraps all requests)
    - Add middleware via `app.add_middleware(RequestLoggingMiddleware)`

    Create `backend/tests/unit/test_request_middleware.py`:
    - Test: response includes X-Request-ID header when none sent
    - Test: response echoes X-Request-ID when client sends one
    - Test: /health requests do NOT produce access log
    - Test: access log contains method, path, status_code, duration_ms
    - Test: middleware emits access log and preserves X-Request-ID on 500 error responses <!-- audit-added -->
    - Test: correlation ID context var is cleaned up after request completes (no leakage between requests) <!-- audit-added -->

    Avoid: Do NOT use Starlette's raw middleware — use BaseHTTPMiddleware for simplicity.
    Avoid: Do NOT log request/response bodies — privacy risk and log volume.
  </action>
  <verify>cd backend && uv run pytest tests/unit/test_request_middleware.py -x -v</verify>
  <done>AC-2, AC-3, AC-4 satisfied: Correlation IDs propagated, access logs emitted, /health excluded</done>
