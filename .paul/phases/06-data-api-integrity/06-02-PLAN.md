<objective>
## Goal
Replace the in-memory `_pending_uploads` dict with a database-backed `pending_uploads` table so the two-step upload flow (request signed URL → process) works reliably when Cloud Run scales to multiple instances.

## Purpose
The upload service uses a module-level `_pending_uploads: dict[str, PendingUpload] = {}` (service.py:118) to track signed URL requests. Cloud Run is configured with `max_instances = 2`. When a second instance handles the `/process` callback, it cannot find the pending upload created on the first instance, causing spurious "Upload ID not found or expired" errors. Fixes AEGIS finding F-08-001.

## Output
- Migration 030: `pending_uploads` table with TTL-based cleanup
- `pending_uploads.py`: Query functions for create/get/delete/cleanup
- `service.py`: Refactored to use DB-backed state instead of in-memory dict
- Unit tests for the new query layer
- Updated integration tests that no longer manipulate the in-memory dict
</objective>

<acceptance_criteria>

## AC-1: Pending uploads are persisted in the database
```gherkin
Given a user requests a signed upload URL
When request_signed_url() completes
Then a row exists in the pending_uploads table with the upload_id, brand_id, file_type, filename, content_type, object_name, and expires_at
And no module-level dict is used for state storage
```

## AC-2: Process atomically claims pending upload from database
```gherkin
Given a pending upload was created on any Cloud Run instance
When process_upload() is called with the upload_id
Then the pending upload is atomically claimed (deleted and returned) from the database
And a second concurrent process_upload() with the same upload_id receives "Upload ID not found or expired"
And processing succeeds with correct brand_id/file_type validation
```
<!-- audit-added: race condition prevention — atomic claim ensures only one instance can process a given upload_id -->

## AC-3: Expired pending uploads are cleaned up
```gherkin
Given pending uploads exist with expires_at in the past
When _cleanup_expired_uploads() runs (triggered on signed-url request)
Then expired rows are deleted from the pending_uploads table
And non-expired rows are unaffected
```

## AC-4: Completed uploads are removed from pending
```gherkin
Given a pending upload exists in the database
When process_upload() completes successfully
Then the pending upload row is already deleted (claimed atomically in AC-2)
```
<!-- audit-added: aligned with atomic claim pattern — deletion happens at claim time, not after processing -->

## AC-5: Expired pending uploads are never returned by queries
```gherkin
Given a pending upload exists with expires_at in the past
When claim_pending_upload() is called with that upload_id
Then None is returned (SQL WHERE expires_at > NOW() filters it)
And the expired row is not processed
```
<!-- audit-added: SQL-level expiry guard provides defense-in-depth alongside Python check -->

    **Migration 030:** Create `pending_uploads` table:
    ```sql
    CREATE TABLE pending_uploads (
        upload_id TEXT PRIMARY KEY,
        brand_id INTEGER NOT NULL REFERENCES brands(id) ON DELETE CASCADE, <!-- audit-added: CASCADE prevents brand deletion from blocking on ephemeral pending rows -->
        file_type TEXT NOT NULL,
        filename TEXT NOT NULL,
        content_type TEXT NOT NULL,
        object_name TEXT NOT NULL,
        expires_at TIMESTAMPTZ NOT NULL,
        created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
    );
    CREATE INDEX idx_pending_uploads_expires_at ON pending_uploads (expires_at);
    ```
    Downgrade: DROP TABLE pending_uploads.

    Follow existing migration pattern from 029_create_audit_log_table.py (Alembic with raw SQL).

    **Query module** `pending_uploads.py`: Create functions:
    - `create_pending_upload(conn, upload_id, brand_id, file_type, filename, content_type, object_name, expires_at)` — INSERT INTO pending_uploads
    - `get_pending_upload(conn, upload_id) -> dict | None` — SELECT by upload_id WHERE expires_at > NOW() <!-- audit-added: SQL-level expiry filter -->
    - `claim_pending_upload(conn, upload_id) -> dict | None` — `DELETE FROM pending_uploads WHERE upload_id = $1 AND expires_at > NOW() RETURNING *`. This is the **primary retrieval method** for process_upload. Atomic delete+return prevents race conditions across Cloud Run instances. <!-- audit-added: atomic claim pattern -->
    - `delete_pending_upload(conn, upload_id)` — DELETE by upload_id (used for explicit cleanup of expired rows found by Python-level checks)
    - `cleanup_expired_uploads(conn) -> int` — DELETE WHERE expires_at < NOW(), return count deleted

    Use parameterized SQL with asyncpg ($1, $2...). Follow patterns from existing `uploads.py` (use `fetch_one`, `fetch_all` from `app.db.queries.utils`).

    Avoid: Adding an auto-increment id column — upload_id (UUID string) is the natural key.
    Avoid: Adding foreign key to users table — the pending upload is pre-auth-completion state.
  </action>

<task type="auto">
  <name>Task 2: Refactor upload service to use DB-backed pending uploads</name>
  <files>backend/app/modules/upload/service.py</files>
  <action>
    Replace all in-memory `_pending_uploads` dict usage with database calls:

    1. **Remove** the module-level `_pending_uploads: dict[str, PendingUpload] = {}` and `_cleanup_expired_uploads()` function
    2. **Keep** the `PendingUpload` dataclass (used as internal DTO)
    3. **Import** `app.db.queries.pending_uploads as pending_queries`

    4. **Refactor `request_signed_url()`:**
       - After generating the signed URL, call `pending_queries.create_pending_upload(conn, ...)` inside the existing `async with db.connection() as conn:` block (reuse the connection from brand lookup, or open a new one)
       - Remove `_pending_uploads[upload_id] = PendingUpload(...)` line
       - Replace `_cleanup_expired_uploads()` call with `await pending_queries.cleanup_expired_uploads(conn)`

    5. **Refactor `_validate_pending_upload()`:** <!-- audit-modified: uses atomic claim instead of get+delete -->
       - Make it `async` (it currently is sync)
       - Accept a `conn` parameter
       - Replace `_pending_uploads.get(upload_id)` with `await pending_queries.claim_pending_upload(conn, upload_id)` — this atomically deletes and returns the row, preventing race conditions across instances
       - Convert the returned dict to a `PendingUpload` dataclass for downstream compatibility
       - Remove the separate expiry check and `_pending_uploads.pop()` on expiry — the SQL `WHERE expires_at > NOW()` handles this; if `claim_pending_upload` returns None, raise the existing "Upload ID not found or expired" error
       - Remove brand_id/file_type mismatch check from this function — move it to `process_upload()` after the claim, since the claim must happen first to prevent races

    6. **Refactor `process_upload()`:** <!-- audit-modified: no separate delete needed, claim is atomic -->
       - Open a DB connection for the pending upload claim
       - Pass `conn` to the now-async `_validate_pending_upload()`
       - After `_validate_pending_upload()` returns the claimed PendingUpload, validate brand_id/file_type match — if mismatch, the row is already consumed (acceptable: the original request was invalid)
       - **Remove** the `_pending_uploads.pop(upload_id, None)` cleanup at the end — the row was already deleted by the atomic claim in step 5

    Avoid: Changing the public API signatures (request_signed_url, process_upload, get_brand_uploads, get_download_url).
    Avoid: Removing the PendingUpload dataclass — it's a useful internal type.
    Avoid: Adding caching or memoization — the DB lookup is a single indexed primary key fetch.
  </action>
