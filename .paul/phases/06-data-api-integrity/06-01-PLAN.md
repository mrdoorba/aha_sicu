<objective>
## Goal
Add transactional atomicity and batch upserts to the sync pipeline so that partial sync failures cannot leave the database in an inconsistent state, and sync performance scales with batch size rather than row count.

## Purpose
Currently, `_sync_sheet_to_table` commits each row individually. If row 50 of 100 fails, rows 1–49 are permanently committed while 50–100 are lost — an inconsistent state with no recovery path. Additionally, 100 brands = 100 DB round-trips, which degrades linearly with data volume. Fixes AEGIS findings F-02-006 (transactional atomicity) and F-08-002 (batch upserts).

## Output
- `brands.py`: New `batch_upsert_brand_data()` function using `executemany()` or bulk INSERT…ON CONFLICT
- `service.py`: `_sync_sheet_to_table` wrapped in `conn.transaction()`, calling batch upsert
- `test_batch_upsert.py`: Unit tests for batch upsert behavior
</objective>

<acceptance_criteria>

## AC-1: Sync is atomic per sheet
```gherkin
Given a sync operation with 100 rows where row 50 causes a database error
When the sync completes
Then zero rows from that sheet are committed to the database
And the sync status records the failure with error details
```

## AC-2: Batch upserts reduce round-trips
```gherkin
Given a sync operation with N rows
When _sync_sheet_to_table executes
Then all valid rows are upserted in a single batch query (not N individual queries)
And the parsed status string confirms the upserted count as an integer
```

## AC-3: Empty and invalid rows are pre-filtered
```gherkin
Given a list of rows where some have empty brand names
When _sync_sheet_to_table processes them
Then rows with empty brand names are excluded before the batch upsert
And the skipped count is accurately reported
```

<!-- audit-added -->
## AC-4: Duplicate brand names within a batch are deduplicated
```gherkin
Given a list of rows where multiple rows share the same brand_name
When _sync_sheet_to_table processes them
Then only the last occurrence of each brand_name is included in the batch
And the upsert completes without "cannot affect row a second time" errors
```

  <name>Task 1: Add batch_upsert_brand_data to brands.py</name>
  <files>backend/app/db/queries/brands.py</files>
  <action>
    Add a new function `batch_upsert_brand_data(conn, table, brand_names, raw_data_list)` that:
    - Accepts `brand_names: list[str]` and `raw_data_list: list[dict[str, Any]]` (parallel arrays, same length)
    - Validates table name against existing `_VALID_TABLES` allowlist
    - Returns the count of upserted rows as an integer
    - Keep the existing `upsert_brand_data` function unchanged (other code may use it)

    Implementation note: asyncpg's `executemany()` does not support RETURNING. Use a single bulk INSERT with unnest arrays for the batch:
    ```sql
    INSERT INTO {table} (brand_name, raw_data, updated_at)
    SELECT unnest($1::text[]), unnest($2::jsonb[]), NOW()
    ON CONFLICT (brand_name) DO UPDATE SET
        raw_data = EXCLUDED.raw_data,
        updated_at = NOW()
    ```
    Pass brand_names as a list[str] and raw_data_list as a list[dict] (asyncpg serializes dicts to jsonb).
    Parse the status string returned by `conn.execute()` (e.g. "INSERT 0 100") to extract the integer count: <!-- audit-added -->
    ```python
    status = await conn.execute(query, brand_names, raw_data_list)
    return int(status.split()[-1])
    ```

    Avoid: Using executemany() — it still issues N round-trips under the hood in asyncpg.
    Avoid: Changing the existing upsert_brand_data signature or behavior.
    Avoid: Returning raw status strings — always return parsed int. <!-- audit-added -->
  </action>

<task type="auto">
  <name>Task 2: Wrap _sync_sheet_to_table in transaction with batch upsert</name>
  <files>backend/app/modules/sync/service.py</files>
  <action>
    Refactor `_sync_sheet_to_table` to:
    1. Pre-filter rows: separate valid rows (non-empty brand name) from skipped rows BEFORE touching the database
    2. Deduplicate by brand_name: if multiple rows share the same brand_name, keep only the LAST occurrence (latest data wins). Track dedup count separately from skip count. <!-- audit-added -->
    3. Build the batch: collect parallel brand_names list and raw_data_list from deduplicated valid rows
    4. Open a connection and start an explicit transaction: `async with db.connection() as conn:` then `async with conn.transaction():`
    5. Call `brand_queries.batch_upsert_brand_data(conn, table, brand_names, raw_data_list)` inside the transaction
    6. If any exception occurs, the transaction auto-rolls back — no partial commits
    7. Log batch operation with structured logging: table name, batch size, skipped count, duration <!-- audit-added -->
    8. Return SheetSyncResult with accurate counts

    The function signature and return type remain unchanged.
    Error handling: If the batch upsert fails, the entire sheet sync fails atomically. The error is captured in SheetSyncResult (success=False, single error entry).

    Avoid: Keeping the row-by-row loop for database writes.
    Avoid: Catching exceptions inside the transaction block (let them propagate to trigger rollback).
    Avoid: Passing duplicate brand_names to batch_upsert — PostgreSQL INSERT...ON CONFLICT cannot affect the same row twice in one statement. <!-- audit-added -->
